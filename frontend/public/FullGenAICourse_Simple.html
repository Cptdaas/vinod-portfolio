Chapter 01 — Introduction to LangChain

What is LangChain?

LangChain is an open-source framework for developing applications powered by large language models (LLMs). It provides modular components and end-to-end tools that help developers build complex AI applications such as chatbots, question-answering systems, RAG, autonomous agents, and more.

Key Advantages

#Feature
1Supports all major LLMs
2Simplifies LLM-based application development
3Integrations for all major tools
4Open source / Free / Actively developed
5Supports all major GenAI use cases

Why LangChain?

Without LangChain, building an AI app that reads a PDF, answers questions, and remembers context requires manually wiring together LLM APIs, document parsing, embedding pipelines, vector databases, and memory. LangChain abstracts all of this with a unified, composable interface.

Example queries LangChain can power:

  • "Explain page number 5 as if I am a 5 year old"
  • "Generate a True/False exercise on Linear Regression"
  • "Generate notes for Decision Trees"

Chapter 03 — Models

The Model Component in LangChain is a crucial part of the framework designed to facilitate interactions with various language models and embedding models. It abstracts the complexity of working directly with different LLMs, providing a uniform interface to communicate with them.

Language Models

Language Models are AI systems designed to process, generate, and understand natural language text.

LLMs (Legacy)

  • General-purpose models for raw text generation
  • Input: plain string → Output: plain string
  • Traditionally older models, less used now

Chat Models (Modern)

  • Specialized for conversational tasks
  • Input: sequence of messages → Output: chat message
  • Used more widely — GPT-4, Claude, Gemini, etc.

Supported Providers (Demo)

ProviderNotes

AnthropicClaude 3, Claude Sonnet
GoogleGemini Pro, Gemini Flash
HuggingFaceOpen-source models via inference API

Open Source Models

Open-source language models are freely available AI models that can be downloaded, modified, fine-tuned, and deployed without restrictions from a central provider.

Unlike closed-source models (GPT-4, Claude, Gemini), open-source models allow full control and customization.

Where to Find Them

  • HuggingFace — the largest repository of open-source LLMs

Ways to Use Open-Source Models

  • Download and run locally (Ollama, llama.cpp)
  • Use via HuggingFace Inference API
  • Self-host on cloud (AWS, GCP, Azure)

Disadvantages

  • Require hardware (GPU) for inference
  • More setup overhead
  • May lag behind proprietary models in quality

Chapter 04 — Prompts

Chapter 04 — Prompts

Prompts are the input instructions or queries given to a model to guide its output. In LangChain, prompts are first-class objects — structured, reusable, and composable.

Static vs Dynamic Prompts

┌──────────────────────────────────────────────────────┐
│  STATIC PROMPT                                        │
│                                                       │
│  "Summarize the Attention Is All You Need paper"      │
│  (hardcoded — not reusable)                           │
└──────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────┐
│  DYNAMIC PROMPT (with PromptTemplate)                 │
│                                                       │
│  "Summarize {paper} in a {style} style,              │
│   with {length} length."                             │
│                                                       │
│  → Filled at runtime from user inputs                 │
└──────────────────────────────────────────────────────┘

PromptTemplate

A PromptTemplate in LangChain is a structured way to create prompts dynamically by inserting variables into a predefined template.

Instead of hardcoding prompts, PromptTemplate allows you to define placeholders that can be filled in at runtime with different inputs. This makes it reusable, flexible, and easy to manage.

Why use PromptTemplate over f-strings?

ReasonExplanation
Default ValidationCatches missing variables before LLM call
ReusableDefine once, use across different inputs
LangChain EcosystemComposable with chains, LCEL, agents

Example

from langchain.prompts import PromptTemplate

template = PromptTemplate(
    input_variables=["paper", "style", "length"],
    template="""Please summarize the research paper titled "{paper}".
Explanation Style: {style}
Explanation Length: {length}
If certain information is not available, respond with: "Insufficient information available"."""
)

prompt = template.format(
    paper="Attention Is All You Need",
    style="Beginner-Friendly",
    length="Medium (3-5 paragraphs)"
)

Messages

In Chat Models, prompts are structured as a sequence of messages, each with a role:

from langchain.prompts import ChatPromptTemplate, MessagesPlaceholder

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful AI tutor."),
    MessagesPlaceholder(variable_name="chat_history"),  # ← injected at runtime

ChatPromptTemplate

ChatPromptTemplate is used to build structured multi-role prompt sequences for Chat Models.

from langchain.prompts import ChatPromptTemplate

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful AI tutor."),
    ("human", "Explain {topic} in simple terms.")
])

MessagesPlaceholder

A MessagesPlaceholder in LangChain is a special placeholder used inside a ChatPromptTemplate to dynamically insert chat history or a list of messages at runtime.

from langchain.prompts import ChatPromptTemplate, MessagesPlaceholder

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder(variable_name="chat_history"),  # ← injected at runtime

Chapter 05 — Structured Output

Chapter 05 — Structured Output

Structured Output is a technique to ensure that language model responses follow a specific, predictable format. This is crucial for building reliable AI applications that need to parse and process model outputs programmatically.

Why Structure?

  • Consistent Responses — Get predictable output format every time
  • Parseable Data — Easy to extract and process information
  • Type Safety — Ensure data types match expectations
  • API Integration — Direct integration with downstream systems

Pydantic Models

Pydantic is a Python library that provides data validation using Python type annotations. It's perfect for defining structured output schemas.

Benefits of Pydantic

  • Type Safety — Automatic type checking and conversion
  • Validation — Built-in validation rules
  • Serialization — Easy JSON serialization/deserialization
  • IDE Support — Autocomplete and type hints

Example Pydantic Model

from pydantic import BaseModel, Field
from typing import List, Optional

class ProductReview(BaseModel):
    product_name: str = Field(description="Name of the product")
    rating: int = Field(description="Rating from 1-5", ge=1, le=5)
    pros: List[str] = Field(description="List of positive points")
    cons: List[str] = Field(description="List of negative points")
    summary: str = Field(description="Brief summary of the review")
    would_recommend: bool = Field(description="Whether the reviewer recommends it")

TypedDict

TypedDict is a lightweight alternative to Pydantic for defining structured output schemas using standard Python typing.

Benefits of TypedDict

  • Lightweight — No additional dependencies
  • Standard Library — Built into Python
  • Simple — Easier for basic use cases

Example TypedDict

from typing import TypedDict, List, Optional

class ProductReview(TypedDict):
    product_name: str
    rating: int  # 1-5
    pros: List[str]
    cons: List[str]
    summary: str
    would_recommend: bool

Use Cases

Data Extraction

Extract structured information from unstructured text:

  • Resume parsing → structured candidate profile
  • Invoice processing → structured financial data
  • News articles → structured event information

API Building

Create reliable APIs that use LLMs as backend:

  • Chatbot responses with structured intents
  • Content generation with metadata
  • Analysis services with structured results

Agents

Structured outputs for agent decision-making:

  • Tool selection with parameters
  • Planning with structured steps
  • Reasoning with logical conclusions

Best Practices

  • Be Specific — Clearly define field descriptions
  • Validate Input — Add constraints and validation rules
  • Handle Errors — Provide fallback for invalid outputs
  • Test Thoroughly — Validate with various inputs

Chapter 06 — Output Parsers

Chapter 06 — Output Parsers

Output Parsers in LangChain help convert raw LLM responses into structured formats like JSON, CSV, Pydantic models, and more. They ensure consistency, validation, and ease of use in applications.

Note: For new applications, prefer with_structured_output() (Chapter 05). Output Parsers are older approach but still widely used and supported.

Output Parser Flow

LLM Raw Response (string)
          │
          ▼
    Output Parser
          │
    ┌─────┴──────┐
    │            │
    ▼            ▼
 Parsed        Validation
 Object        Error (if invalid)

1. StrOutputParser

The simplest output parser. Takes LLM output and returns it as a plain string. Useful when you just want clean text without any structure.

from langchain_core.output_parsers import StrOutputParser

chain = prompt | llm | StrOutputParser()
result = chain.invoke({"topic": "LangChain"})
# result is a plain string

When to use: Any time you just want raw text response — no structure needed.

2. JSONOutputParser

Parses LLM output as JSON. The LLM must be prompted to return valid JSON.

from langchain_core.output_parsers import JsonOutputParser

parser = JsonOutputParser()
chain = prompt | llm | parser
result = chain.invoke({"text": "Review text here"})
# result is a Python dict

3. StructuredOutputParser

StructuredOutputParser helps extract structured JSON data from LLM responses based on predefined field schemas (ResponseSchema).

from langchain.output_parsers import StructuredOutputParser, ResponseSchema

schemas = [
    ResponseSchema(name="summary", description="Brief overview"),
    ResponseSchema(name="sentiment", description="positive, neutral, or negative"),
]

parser = StructuredOutputParser.from_response_schemas(schemas)
format_instructions = parser.get_format_instructions()
# Inject format_instructions into your prompt

How it works:

  1. Define fields with ResponseSchema
  2. Get format instructions → inject into prompt
  3. LLM returns a formatted JSON string
  4. Parser extracts and validates fields

4. PydanticOutputParser

Parses LLM output into a Pydantic model instance — giving you full type safety and validation.

from langchain.output_parsers import PydanticOutputParser from pydantic import BaseModel, Field class Joke(BaseModel): setup: str = Field(description="The setup of joke") punchline: str = Field(description="The punchline of joke") parser = PydanticOutputParser(pydantic_object=Joke) format_instructions = parser.get_format_instructions()

Comparison

ParserOutput TypeValidationUse Case

JsonOutputParserdictJSON validityFlexible JSON
StructuredOutputParserdictField presenceNamed fields
PydanticOutputParserPydantic objectFull type checkType-safe structured data

Chapter 07 — Chains

Chapter 07 — Chains

A Chain in LangChain connects multiple components into a pipeline where output of one step becomes the input of the next. Chains are the core composition mechanism in LangChain.

Why Chains?

Without chains, you manually pass outputs between components:

prompt = template.format(topic="AI")
response = llm.invoke(prompt)
result = parser.parse(response)

With chains (via LCEL | operator):

chain = template | llm | parser
result = chain.invoke({"topic": "AI"})

1. Simple Chain

A single prompt → LLM → output parser pipeline.

Input
  │
  ▼
┌─────────────────┐
│  Prompt Template │
└────────┬─────────┘
         │
         ▼
┌─────────────────┐
│   LLM / Chat    │
└────────┬─────────┘
         │
         ▼
┌─────────────────┐
│  Output Parser  │
└────────┬─────────┘
         │
         ▼
      Output

2. Sequential Chain

The output of one chain feeds as input into the next chain. Useful for multi-step reasoning.

Input
  │
  ▼
┌──────────────┐
│   Chain 1    │  (e.g., Generate outline)
└──────┬───────┘
       │ Output 1
       ▼
┌──────────────┐
│   Chain 2    │  (e.g., Expand outline into full text)
└──────┬───────┘
       │ Output 2
       ▼
┌──────────────┐
│   Chain 3    │  (e.g., Translate result)
└──────┬───────┘
       │
       ▼
    Final Output

3. Parallel Chain

Multiple chains run simultaneously on the same input. Their outputs are merged into a dictionary.

           Input
             │
    ┌────────┼────────┐
    ▼        ▼        ▼
┌───────┐ ┌───────┐ ┌───────┐
│Chain A│ │Chain B│ │Chain C│
│(pros) │ │(cons) │ │(summ.)│
└───┬───┘ └───┬───┘ └───┬───┘
    └────────┬─────────┘
             ▼
    { pros: ..., cons: ..., summary: ... }

When to use: Running multiple independent analyses on the same input — saves time by running in parallel.

4. Conditional Chain

Routes to different chains based on conditions — like an if/elif/else for pipelines.

Input
  │
  ▼
┌─────────────────┐
│  Router / Check │
└──────┬──────────┘
       │
  ┌────┴─────┐
  │          │
  ▼          ▼
[technical] [simple]
  Chain      Chain
  │          │
  └────┬─────┘
       ▼
    Output

Example: If the question is technical → use a detailed prompt. If it's casual → use a simple prompt.

Chain Summary

Chain TypeUse Case
SimpleSingle-step prompt → response
SequentialMulti-step, each step builds on previous
ParallelMultiple independent analyses at once
ConditionalRoute to different logic based on input

Chapter 08 — Runnables & LCEL

Chapter 08 — Runnables & LCEL

What are Runnables?

A Runnable is any LangChain component that implements a standard interface with .invoke(), .stream(), and .batch() methods. Runnables are the building blocks of LCEL pipelines.

Every LangChain component — prompts, LLMs, output parsers, retrievers — is a Runnable.

LCEL — LangChain Expression Language

LCEL is a declarative way to compose Runnables using | (pipe) operator, inspired by Unix pipes.

chain = prompt | llm | parser
result = chain.invoke({"topic": "AI"})

The | operator creates a RunnableSequence automatically.

The Five Runnable Primitives

┌─────────────────────────────────────────────────────────────┐
│                    Runnable Primitives                       │
│                                                              │
│  1. RunnableSequence   → A | B | C  (sequential)            │
│  2. RunnableParallel   → {a: A, b: B}  (parallel)           │
│  3. RunnablePassthrough → pass input unchanged              │
│  4. RunnableLambda     → wrap custom Python function         │
│  5. RunnableBranch     → conditional routing (if/elif/else)  │
└─────────────────────────────────────────────────────────────┘

1. RunnableSequence

Executes each step one after another, passing the output of one as input to the next.

Input → [Step A] → [Step B] → [Step C] → Output
from langchain_core.runnables import RunnableSequence

chain = RunnableSequence(prompt, llm, parser)
# OR using pipe operator:
chain = prompt | llm | parser

Use when: You need ordered, step-by-step processing.

2. RunnableParallel

Runs multiple runnables simultaneously on the same input. Each produces its own output, collected into a dict.

             Input
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
   [Task A] [Task B] [Task C]
      │        │        │
      └────────┼────────┘
               ▼
  { "a": result_a, "b": result_b, "c": result_c }
            
from langchain_core.runnables import RunnableParallel

parallel = RunnableParallel({
    "pros": pros_chain,
    "cons": cons_chain,
    "summary": summary_chain
})

3. RunnablePassthrough

Simply returns the input unchanged. Used to pass original data alongside transformed data.

Input → [RunnablePassthrough] → Same Input (unchanged)
from langchain_core.runnables import RunnablePassthrough

chain = RunnableParallel({
    "context": retriever,
    "question": RunnablePassthrough()  # ← passes original question through
})

Common RAG pattern:

rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
    | parser
)

4. RunnableLambda

Wraps a custom Python function so it can be used as a step in an LCEL pipeline. Acts as middleware for preprocessing, transformation, filtering, or post-processing.

from langchain_core.runnables import RunnableLambda

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

format_chain = RunnableLambda(format_docs)

chain = retriever | RunnableLambda(format_docs) | prompt | llm

5. RunnableBranch

A control flow component that conditionally routes input to different chains based on custom logic. Functions like if/elif/else for pipelines.

Input
  │
  ▼
┌─────────────────────────┐
│     RunnableBranch      │
│                         │
│  if condition_1 → Chain1│
│  elif condition_2 →Chain2│
│  else (default) → Chain3│
└──────────┬──────────────┘
           │
           ▼
        Output
            
from langchain_core.runnables import RunnableBranch

branch = RunnableBranch(
    (lambda x: "technical" in x["topic"], technical_chain),
    (lambda x: "simple" in x["topic"], simple_chain),
    default_chain  # fallback
)

Runnable Methods

All runnables support these methods:

MethodDescription
.invoke(input)Run synchronously, return result
.stream(input)Stream output token by token
.batch([input1, input2])Run multiple inputs in parallel
.ainvoke(input)Async version of invoke
.astream(input)Async streaming

Chapter 09 — RAG Pipeline

Chapter 09 — RAG Pipeline

RAG (Retrieval Augmented Generation) is a technique that combines information retrieval with language generation, where a model retrieves relevant documents from a knowledge base and uses them as context to generate accurate and grounded responses.

Why RAG?

BenefitDescription
Up-to-date informationAccess knowledge beyond LLM's training cutoff
Better privacyKeep data in your own vector store, not sent to LLM training
No document size limitIndex unlimited documents; retrieve only what's needed

RAG Overview Flow

┌──────────────────────────────────────────────────────────────┐
│                        RAG Pipeline                           │
│                                                               │
│  INDEXING PHASE (done once / periodically)                    │
│  ─────────────────────────────────────────                    │
│  Raw Docs                                                     │
│     │                                                         │
│     ▼                                                         │
│  [Document Loader]  ← PDF, Web, CSV, TXT, etc.               │
│     │                                                         │
│     ▼                                                         │
│  [Text Splitter]    ← Break into chunks                       │
│     │                                                         │
│     ▼                                                         │
│  [Embedding Model]  ← Convert chunks to vectors              │
│     │                                                         │
│     ▼                                                         │
│  [Vector Store]     ← Store vectors (Chroma/Pinecone/FAISS)  │
│                                                               │
│  RETRIEVAL + GENERATION PHASE (at query time)                 │
│  ─────────────────────────────────────────────                │
│  User Query                                                   │
│     │                                                         │
│     ▼                                                         │
│  [Retriever]        ← Similarity search in vector store      │
│     │                                                         │
│     ▼                                                         │
│  Retrieved Chunks                                             │
│     │                                                         │
│     ▼                                                         │
│  [Prompt Template]  ← Augment query with context             │
│     │                                                         │
│     ▼                                                         │
│  [LLM]              ← Generate grounded answer               │
│     │                                                         │
│     ▼                                                         │
│  Final Answer                                                 │
└──────────────────────────────────────────────────────────────┘

Part 1 — Document Loaders

Document loaders are components in LangChain used to load data from various sources into a standardized format (usually as Document objects).

Available Loaders

LoaderSourceNotes
TextLoader.txt filesSimple, only plain text
PyPDFLoaderPDF filesEach page → one Document

TextLoader

from langchain_community.document_loaders import TextLoader

loader = TextLoader("notes.txt")
docs = loader.load()  # Returns List[Document]

PyPDFLoader

from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("document.pdf")

from langchain_community.document_loaders import WebBaseLoader

Part 2 — Text Splitters

Text Splitting is the process of breaking large chunks of text into smaller, manageable chunks that an LLM or embedding model can handle effectively.

Why Split?

  • Overcome model input size limits
  • Improve retrieval precision (smaller chunks = more targeted results)
  • Optimize memory and computation

4 Types of Text Splitting

┌──────────────────────────────────────────────────────────┐
│              Text Splitting Strategies                    │
│                                                          │
│  1. Length Based      → Split by character/token count  │
│  2. Text Structure    → Split by separators (\n, \n\n)  │
│  3. Document Structure→ Split by Markdown/HTML sections │
│  4. Semantic Meaning  → Split by meaning similarity     │
└──────────────────────────────────────────────────────────┘

1. Length-Based Splitting

Split every N characters regardless of content.

from langchain.text_splitter import CharacterTextSplitter

splitter = CharacterTextSplitter(chunk_size=200, chunk_overlap=20)
chunks = splitter.split_text(text)

2. Text-Structure Based (RecursiveCharacterTextSplitter)

Tries to split on natural boundaries: \n\n → \n → ` ` → character.

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)

3. Document-Structure Based

Respects document structure — splits on Markdown headers, HTML tags, etc.

from langchain.text_splitter import MarkdownHeaderTextSplitter

splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "H1"), ("##", "H2")])

4. Semantic Meaning Based

Groups sentences that are semantically similar together — most intelligent but slowest.

Part 3 — Vector Stores

A vector store is a system designed to store and retrieve data represented as numerical vectors.

Key Features

FeatureDescription
StorageRetain vectors + metadata in-memory or on-disk
Similarity SearchFind vectors most similar to a query vector
IndexingFast ANN (Approximate Nearest Neighbor) lookups
CRUD OperationsAdd, read, update, delete vectors

Vector Store vs Vector Database

Vector StoreVector Database
ScaleLightweight, prototypingProduction, large datasets
FeaturesBasic CRUD + searchDistributed, ACID, auth, backups
ExamplesFAISS, ChromaPinecone, Milvus, Qdrant, Weaviate

Chroma (Recommended for Development)

Chroma is a lightweight, open-source vector database, ideal for local development and small-to-medium scale needs.

from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=OpenAIEmbeddings()
)

LangChain integrates with: FAISS, Pinecone, Chroma, Qdrant, Weaviate, and more. A common interface lets you swap backends with minimal code changes.

Part 4 — Retrievers

A retriever is a component that fetches relevant documents from a data source in response to a user's query. All retrievers in LangChain are Runnables.

Types of Retrievers

┌──────────────────────────────────────────────────────────────┐
│                     Retriever Types                          │
├──────────────────────────┬───────────────────────────────────┤
│  VectorStoreRetriever    │ Semantic similarity search        │
│  WikipediaRetriever      │ Queries Wikipedia API             │
│  MMR Retriever           │ Relevance + diversity balance     │
│  MultiQueryRetriever     │ Generates multiple query variants │
│  ContextualCompression   │ Compresses retrieved docs         │
└──────────────────────────┴───────────────────────────────────┘

Vector Store Retriever (Most Common)

retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
docs = retriever.invoke("What is LangChain?")

MMR — Maximal Marginal Relevance

An algorithm that reduces redundancy while maintaining relevance. Instead of returning top-K most similar, it balances similarity with diversity.

retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 5, "fetch_k": 20}
)

Multi-Query Retriever

Uses an LLM to generate multiple variants of the user's query, retrieves documents for each, and combines results for broader coverage.

Contextual Compression Retriever

After retrieval, this retriever compresses documents — keeping only the relevant parts of each chunk based on the query. Reduces noise sent to LLM.

Part 5 — Full RAG Chain (LangChain Implementation)

from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain.prompts import ChatPromptTemplate

# Prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant. Use the following context to answer the question.\n\nContext: {context}"),
    ("human", "{question}")
])

# Format retrieved docs
def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

# Full RAG Chain
rag_chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough()
    }
    | prompt
    | llm
    | StrOutputParser()
)

answer = rag_chain.invoke("What is LangChain?")

Chapter 10 — Tools & Tool Calling

What is a Tool?

A tool is just a Python function (or API) that is packaged in a way LLM can understand and call when needed.

┌──────────────────────────────────────────────────────┐
│                How Tools Fit in Agents               │
│                                                      │
│  User Query                                          │
│      │                                               │
│      ▼                                               │
│  ┌─────────┐    decides to call    ┌──────────────┐ │
│  │   LLM   │ ─────────────────────▶│    Tool      │ │
│  │ (Agent) │                       │ (Python fn / │ │
│  └─────────┘ ◀─────────────────── │  API)        │ │
│      │          tool result        └──────────────┘ │
│      ▼                                               │
│  Final Answer                                        │
└──────────────────────────────────────────────────────┘

Built-in Tools

A built-in tool is a tool that LangChain already provides for you — pre-built, production-ready, and requires minimal or no setup. You don't have to write the function logic yourself — you just import and use it.

ToolWhat It Does
DuckDuckGoSearchRunWeb search via DuckDuckGo
WikipediaQueryRunWikipedia summary
PythonREPLToolRun raw Python code
ShellToolRun shell commands
RequestsGetToolMake HTTP GET requests
GmailSendMessageToolSend emails via Gmail
SlackSendMessageToolPost message to Slack
SQLDatabaseQueryToolRun SQL queries
from langchain_community.tools import DuckDuckGoSearchRun

search = DuckDuckGoSearchRun()
result = search.invoke("Latest news on LangChain")

Custom Tools

A custom tool is a tool that you define yourself. Use them when:

  • You want to call your own APIs
  • You want to encapsulate business logic
  • You want LLM to interact with your database, product, or app

Ways to Create Custom Tools

┌─────────────────────────────────────────────────────┐
│           Custom Tool Creation Methods              │
│                                                     │
│  1. @tool decorator     ← Simplest, most common     │
│  2. StructuredTool      ← Multi-argument tools      │
│  3. BaseTool class      ← Full control / advanced   │
└─────────────────────────────────────────────────────┘

1. @tool Decorator

The simplest way — just decorate a Python function and LangChain wraps it automatically.

from langchain.tools import tool

@tool
def get_weather(city: str) -> str:
    """Get current weather for a given city."""
    # Your API call here
    return f"Weather in {city}: Sunny, 25°C"

The docstring becomes the tool's description — the LLM uses it to decide when to call the tool.

2. StructuredTool

A StructuredTool is a special type of tool where the input follows a structured schema, typically defined using a Pydantic model. Use when your tool takes multiple typed arguments.

from langchain.tools import StructuredTool
from pydantic import BaseModel

class WeatherInput(BaseModel):
    city: str
    unit: str = "celsius"

def get_weather(city: str, unit: str = "celsius") -> str:
    """Get weather for a city in specified unit."""
    return f"Weather in {city}: 25°{unit[0].upper()}"

tool = StructuredTool.from_function(
    func=get_weather,
    args_schema=WeatherInput
)

3. BaseTool (Abstract Base Class)

BaseTool is the abstract base class for all tools in LangChain. It defines the core structure and interface that any tool must follow.

All other tool types like @tool and StructuredTool are built on top of BaseTool.

Use BaseTool when you need:

  • Full control over tool behavior and error handling
  • Async tool execution
  • Custom tool logic that doesn't fit a simple function
from langchain.tools import BaseTool
from typing import Optional

class CurrencyConverterTool(BaseTool):
    name: str = "currency_converter"
    description: str = "Converts an amount from one currency to another"

    def _run(self, amount: float, from_currency: str, to_currency: str) -> str:
        # Your conversion logic here
        return f"{amount} {from_currency} = X {to_currency}"

    async def _arun(self, *args, **kwargs):
        raise NotImplementedError("Async not supported")

Inheritance Hierarchy

BaseTool  (abstract base)
    │
    ├── @tool  (decorator — simplest)
    │
    └── StructuredTool  (Pydantic schema input)

Toolkits

A toolkit is a collection (bundle) of related tools that serve a common purpose — packaged together for convenience and reusability.

GoogleDriveToolKit
    │
    ├── GoogleDriveCreateFileTool   → Upload a file
    ├── GoogleDriveSearchTool       → Search by name/content
    └── GoogleDriveReadFileTool     → Read file contents
            
from langchain_google_community import GoogleDriveToolkit

toolkit = GoogleDriveToolkit()
tools = toolkit.get_tools()  # List of individual tool objects

Tool Calling Pipeline

Step 1 — Tool Binding

Tell the LLM which tools are available.

llm_with_tools = llm.bind_tools([get_weather, search_web])

Step 2 — Tool Calling

The LLM decides to call a tool and returns a structured tool call instead of a text response.

response = llm_with_tools.invoke("What's the weather in Delhi?")
# response contains tool_calls, not final answer yet

Step 3 — Tool Execution

Extract the tool call, execute the actual function, and return the result.

tool_call = response.tool_calls[0]
tool_name = tool_call["name"]
tool_args = tool_call["args"]

# Execute tool
result = tool_map[tool_name].invoke(tool_args)

User Query
    │
    ▼
LLM (with tools bound)
    │
    ├── If no tool needed → Direct Answer
    │
    └── If tool needed
            │
            ▼
        Tool Call (name + args)
            │
            ▼
        Tool Execution (Python function)
            │
            ▼
        Tool Result
            │
            ▼

            │
